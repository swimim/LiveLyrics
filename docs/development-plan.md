# MediaRemote + LRCLIB 기반 macOS 동기화 가사 앱 개발 계획서

작성일: 2026-10-14 · 대상: 고등학생 개인 개발 프로젝트 · 개발 방식: Codex를 활용한 바이브코딩

## 1. 프로젝트 개요와 목표

macOS에서 재생 중인 음악 정보를 읽고, LRCLIB에서 해당 곡의 가사를 받아 현재 재생 위치에 맞는 가사 줄을 보여 주는 네이티브 앱을 만든다. 가칭은 **LyricBar**로 정한다.

사용 흐름은 **앱 실행 → 음악 재생 → 화면 오른쪽 위에 가사 자동 표시**다. 화면을 가로 2열·세로 3행의 6개 칸으로 나눴을 때 오른쪽 위 칸을 가사 영역으로 사용한다. 완전히 투명한 배경 위에 불투명한 회색 이탤릭 가사를 표시하며, 현재 가사는 흰색으로 강조한다. 현재 줄을 영역의 중앙에 유지하고, 다음 줄로 넘어갈 때 기존 가사가 위로 밀리며 아래에서 새 줄이 올라오는 Spotify 가사 화면과 유사한 흐름을 구현한다. 메뉴바 클릭은 가사를 보기 위한 조건이 아니다.

학습 목표는 Swift 문법을 모두 익힌 뒤 시작하는 것이 아니라, Codex가 만든 작은 변경을 읽고 실행하면서 비동기 API 요청, 데이터 파싱, 상태 관리, 시간 동기화, 오류 처리를 이해하는 것이다. 학생은 제품 범위·검증·최종 판단을 담당하고 Codex는 구현·설명·테스트 작성·문제 분석을 돕는다.

### 성공 기준

- 개발자의 실제 Mac과 음악 앱 1종에서 현재 곡, 재생 상태, 재생 위치를 안정적으로 읽는다.
- 동기화 가사가 있는 곡은 오른쪽 위 1/6 영역에서 현재 줄을 흰색으로 중앙에 표시하고, 앞뒤 줄은 불투명한 회색 이탤릭으로 표시한다.
- 다음 가사 전환 시 위로 슬라이딩하며, 일시 정지·재개·탐색·곡 변경에도 중앙 기준을 유지한다.
- 가사가 없거나 네트워크가 끊겨도 앱이 종료되지 않고 이유를 표시한다.
- 합성 가사와 모의 재생기로 인터넷 없이 발표할 수 있다.
- 핵심 구조와 동기화 수식을 학생이 설명할 수 있다.

**완성 범위는 모든 음악 앱을 지원하는 상용 제품이 아니라, 검증한 환경에서 작동하는 학습용 MVP다.**

## 2. 먼저 확인해야 할 기술적 전제

### MediaRemote는 첫 번째 검증 과제다

MediaRemote는 비공개 프레임워크다. 공개 구현에서는 macOS 15.4부터 앱 내부의 직접 로딩 방식에 제약이 생겼다고 보고한다. 기존 대화의 ‘MediaRemote에서 바로 곡 정보를 얻는다’는 전제를 현재 환경에 그대로 적용하면 안 된다. 해당 내용은 Apple의 지원 약속이 아닌 공개 구현자의 관찰이다. [MediaRemote Adapter 원본](https://github.com/ungive/mediaremote-adapter)

따라서 개발 시작 단계에서 **실제 OS 빌드·Xcode 버전·음악 앱 버전·서명 방식**을 기록하고 작은 연동 실험을 한다. 시스템 전체 Now Playing 정보는 음악 앱이 제공한 정보에 의존하므로 모든 앱·브라우저·재생 상태를 동일하게 읽는다고 보장하지 않는다.

진행 경로는 다음과 같다.

1. **주 경로:** 검토한 MediaRemote 어댑터를 얇은 Swift 래퍼로 감싸 실제 기기에서 검증한다.
2. **제한적 대안:** 실패하면 Apple Music 또는 Spotify 한 앱의 AppleScript 인터페이스를 조사해 전용 공급자로 대체한다. 이 경우 결과물은 ‘MediaRemote 연동 실험 및 앱별 대체 구현’으로 명시한다.
3. **발표 보장 경로:** 실제 연동과 별도로 모의 재생 공급자를 유지한다. 모의 동작을 실제 MediaRemote 성공으로 보고하지 않는다.

SIP 해제, 시스템 데몬 코드 주입, 관리자 권한을 요구하는 우회 방식은 프로젝트 범위에서 제외한다. 최소 연동 실험에서 호환성 문제가 해결되지 않으면 원인을 기록하고 대체 공급자로 전환한다.

### 최신 LRCLIB 문서를 기준으로 한다

확인일 기준 공식 문서는 익명 접근과 API 키 없는 사용을 지원하지만 **클라이언트 식별 헤더와 요청 제한 대응을 요구**한다. `/api/get`의 제목·아티스트는 필수이고 앨범·재생 시간은 선택이나 매칭 정확도를 위해 권장된다. 오래된 예제의 ‘제한 없음’ 또는 ‘모든 인자가 필수’라는 설명을 그대로 사용하지 않는다. [LRCLIB 공식 API 문서](https://lrclib.net/docs)

배포 대상은 **macOS 14 이상을 초기 설정 후보**로 삼되, 실제 지원은 보유 Mac에서 검증한 버전으로 한정한다. OS 최소 버전과 MediaRemote 동작 보장은 서로 다른 문제다. 두 번째 Mac이나 Intel 기기가 없으면 그 환경은 ‘미검증’으로 남긴다.

AppKit 패널에 SwiftUI 가사 View를 넣고 창 배치와 텍스트 렌더링을 분리한다. 설정·종료는 별도 제어 창에 제공하고, 앱을 다시 활성화하면 이 창에 접근할 수 있게 한다. [Apple NSPanel 문서](https://developer.apple.com/documentation/appkit/nspanel)

## 5. 전체 아키텍처

하나의 앱 타깃 안에서 폴더와 프로토콜로 책임을 나눈다. 초기부터 여러 패키지나 복잡한 의존성 주입 프레임워크를 만들지 않는다.

```text
음악 앱 → macOS Now Playing
                 ↓
         MediaRemote 어댑터
                 ↓
        NowPlayingProvider ← Mock / 앱별 대체 공급자
                 ↓
       AppModel / 곡 변경 조정
          ├─ 곡 정보 → LyricsRepository → 메모리 캐시
          │                    ↓ 캐시 없음
          │              LRCLIBClient → HTTPS → LRCLIB
          │                    ↓
          │              Matcher → LRCParser
          │                         ↓
          └─ 재생 스냅샷 → PlaybackClock → LyricsSynchronizer
                                            ↓
                                   현재 가사 그룹 인덱스
                                            ↓
                              OverlayLayout → SwiftUI 가사 + 투명 NSPanel
```

UI는 MediaRemote 원본 딕셔너리나 API JSON을 직접 읽지 않는다. 네트워크 대기·파싱은 UI를 막지 않고, 화면 상태 변경만 MainActor에서 수행한다.

## 6. 데이터 흐름과 상태 전이

1. 앱 시작 시 투명 오버레이를 준비하고 공급자를 시작해 현재 스냅샷을 한 번 요청한다. 가사 표시는 자동으로 이루어진다.
2. 이벤트를 자체 모델로 변환한다. 제목·아티스트가 부족하면 조회하지 않고 ‘곡 정보 확인 중’을 표시한다.
3. 재생 시간만 바뀐 이벤트는 시계만 갱신한다. 곡 식별 정보가 바뀌면 가사 조회를 시작한다.
4. 곡 변경 직후 약 300ms 동안 메타데이터가 안정되는지 확인한다. 다른 곡의 앨범·길이가 섞이지 않게 한다.
5. 새 조회 세대 번호를 만들고 이전 요청을 취소한다. 이전 가사와 인덱스를 즉시 지운다.
6. 캐시를 확인한 뒤 필요하면 LRCLIB에 요청한다. 반환 결과의 제목·아티스트·버전·길이를 검증한다.
7. 동기화 가사를 파싱하거나 일반 가사·연주곡·미등록 상태로 전환한다.
8. 가사가 도착한 시점의 현재 재생 위치로 곧바로 맞춘다. 첫 줄부터 재생하지 않는다.
9. 응답 적용 전에 곡 키와 조회 세대 번호를 모두 비교한다. 취소가 늦어져도 과거 응답이 화면을 덮지 못하게 한다.

```text
곡 없음 → 정보 대기 → 가사 로딩 → 동기화 가사
                              ├→ 일반 가사
                              ├→ 연주곡
                              ├→ 가사 없음 / 후보 확인 필요
                              └→ 통신 실패

별도 상태: 공급자 연결 실패 / 재생 중 / 일시 정지 / 재생 위치 불명
```

가사 상태와 재생 상태를 분리한다. ‘일시 정지’ 때문에 받아 둔 가사가 사라지거나, ‘오프라인’ 때문에 이미 표시 중인 가사가 초기화되지 않게 한다.

## 7. 모듈 설계

| 모듈 | 책임 | 경계와 주의점 |
| --- | --- | --- |
| NowPlayingProvider | 스냅샷 스트림, 시작·종료·재조회 | 실제 공급자와 Mock이 같은 계약 사용 |
| MediaRemoteProvider | 어댑터 이벤트·단위·누락값 변환 | 비공개 심볼·프로세스 세부 사항을 외부로 노출하지 않음 |
| TrackIdentity | 곡 식별과 조회 입력 구성 | 재생 위치를 키에 넣지 않음 |
| LRCLIBClient | 요청 생성, HTTP 검증, JSON 디코딩 | 가사 선택과 UI 상태를 결정하지 않음 |
| LyricsMatcher | 곡 정보와 후보 일치 여부 판단 | 첫 검색 결과를 무조건 선택하지 않음 |
| LyricsRepository | 캐시, 중복 요청, 재시도 제한 | 같은 곡의 요청을 공유 |
| LRCParser | 문자열을 시간별 가사 그룹으로 변환 | 네트워크·UI에 의존하지 않는 순수 로직 |
| PlaybackClock | 기준 위치·시간·속도로 현재 위치 계산 | 시계 주입으로 테스트 가능하게 구성 |
| LyricsSynchronizer | 현재 위치에 해당하는 그룹 찾기 | 역방향 탐색도 처리 |
| AppModel | 전체 상태 전이, 요청 세대, 화면 데이터 | MainActor에서 관리 |
| OverlayLayout | 오른쪽 위 1/6 영역 계산, 줄 높이·중앙 위치 측정 | 화면 크기 변경과 긴 가사 처리 |
| LyricsTransitionController | 현재 인덱스 기반 슬라이딩·중단·재배치 | 애니메이션을 재생 시계로 사용하지 않음 |
| Views / PanelController | 투명 창, 가사 렌더링, 클릭 통과, 창 수명 | View 재생성 시 공급자를 중복 시작하지 않음 |

권장 폴더: `App/`, `Models/`, `NowPlaying/`, `Lyrics/`, `Playback/`, `Views/`, `Tests/Fixtures/`. 처음에는 파일 수를 최소화하고 책임이 실제로 커질 때 분리한다.

## 8. 주요 데이터 모델

다음은 구현 계약을 설명하기 위한 모델 초안이다. 완성된 앱 코드가 아니다.

```swift
struct TrackMetadata: Equatable, Sendable {
    let sourceBundleID: String?
    let sourceTrackID: String?
    let title: String
    let artist: String
    let album: String?
    let durationSeconds: Double?
}

enum PlaybackState: Sendable {
    case playing, paused, stopped, unknown
}

struct PlaybackSnapshot: Sendable {
    let track: TrackMetadata?
    let elapsedAtAnchor: Double?
    let anchor: ContinuousClock.Instant
    let rate: Double?
    let state: PlaybackState
}

struct LRCLIBRecord: Decodable, Sendable {
    let id: Int
    let trackName: String
    let artistName: String
    let albumName: String
    let duration: Double
    let instrumental: Bool
    let plainLyrics: String?
    let syncedLyrics: String?
}

struct LyricCue: Identifiable, Sendable {
    let id: Int
    let startSeconds: Double
    let texts: [String] // 같은 시각의 여러 가사 줄
}

struct LyricsDocument: Sendable {
    let recordID: Int?
    let cues: [LyricCue]
    let plainText: String?
    let fileOffsetMilliseconds: Int
    let instrumental: Bool
}

enum LyricsState {
    case idle, loading, notFound, needsSelection
    case synced(LyricsDocument)
    case plain(String)
    case instrumental
    case failed(String)
}
```

`LRCLIBRecord`는 MVP에 필요한 필드만 디코딩한다. 현재 문서에 있는 `hasWordSync`, `lyricsfile` 같은 추가 필드는 무시하고 줄 단위 `syncedLyrics`를 사용한다. 필드 추가만으로 앱이 실패하지 않게 한다. [LRCLIB 응답 필드](https://lrclib.net/docs#lyrics-record-fields)

곡 키는 공급자의 안정적인 ID가 있으면 우선 사용하고, 없으면 출처·제목·아티스트·앨범으로 구성한다. 메타데이터 수정과 유효 길이 변경은 조회 입력 버전을 갱신하지만, 소수점 길이 흔들림이 매번 새 곡으로 처리되지 않도록 한다. 검색용 문자열과 원본 표시 문자열은 따로 보존한다.

오버레이 상태는 `activeCueID`, `targetCueID`, `measuredCueHeights`, `viewportSize`, `transitionGeneration`으로 관리한다. 줄 ID는 곡 키와 cue ID의 조합으로 만들고, 매 프레임 새 ID를 만들지 않는다. 현재 줄 판정은 재생 모델이, 이동 중인 화면 좌표는 표현 모델이 담당한다.

캐시에는 곡 서명, 공급자 레코드 ID, 조회 시각, 파싱 결과를 저장한다. 보정값은 별도 설정으로 두어 같은 가사를 다시 파싱할 필요가 없게 한다.

## 9. MediaRemote 연동 방식

### 9.1 권장 접근

Swift 패키지 형태의 어댑터를 후보로 검토한다. 예를 들어 `ejbills/mediaremote-adapter`는 수신 콜백, 단발 조회, 리스너 종료·디코딩 오류 콜백을 제공한다. 내부적으로 시스템 Perl과 보조 프레임워크를 이용하는 방식이므로 UI가 Swift 네이티브라는 사실과 실행 경로가 순수 Swift라는 주장은 구분해야 한다. [Swift 어댑터 README](https://github.com/ejbills/mediaremote-adapter)

패키지 채택 전 라이선스·포함 바이너리 출처·빌드 방법을 확인하고 커밋을 고정한다. 라이선스가 불명확하면 코드나 바이너리를 재배포하지 않고 다른 후보를 검토한다. README의 호환성 문구만으로 최신 macOS 지원을 확정하지 않는다.

직접 `dlopen`/`dlsym`으로 `MRMediaRemoteGetNowPlayingInfo` 등의 비공개 심볼을 호출하는 방식은 선택적 연구 항목이다. 심볼 존재 확인만으로 실제 응답 수신을 보장할 수 없고 함수 시그니처가 틀리면 크래시할 수 있어, 초보자 MVP의 기본 구현으로 삼지 않는다.

### 9.2 첫 실험의 확인 항목

- 제목·아티스트·앨범·길이·위치·속도·재생 상태·출처 앱을 화면이나 임시 로그로 관찰한다.
- 30초 재생, 10초 정지, 재개, 앞뒤 탐색, 다음 곡, 같은 곡 반복을 확인한다.
- 음악 앱 종료, 앱 전환, Mac 잠자기·복귀를 확인한다.
- Debug 실행과 빌드된 `.app` 직접 실행을 각각 검사한다.
- 개발 기기의 샌드박스·서명 설정과 실패 로그를 기록한다.

### 9.3 이벤트와 시간 변환

이벤트 구독을 우선하고, 필요할 때만 재조회한다. 재생 중 3~5초 간격의 보정 조회는 실험 결과 이벤트 누락이 있을 때 추가한다. 재생 세션이 없으면 더 긴 간격으로 낮춘다. 리스너의 무응답은 정지 상태에서도 정상일 수 있으므로 ‘이벤트가 없음’만으로 프로세스를 계속 재시작하지 않는다.

어댑터의 마이크로초는 초로 변환한다. 원본의 기준 시각이 Unix 시간인지 다른 기준인지 해당 버전 소스로 확인한다. `currentElapsedTime`처럼 이미 보간된 값을 사용하면 수신 시점의 단조 시계에 고정하고 **같은 경과 시간을 다시 더하지 않는다**. 원시 위치와 원시 기준 시각을 쓰는 경로는 별도로 구현한다. [어댑터 시간 필드 설명](https://github.com/ejbills/mediaremote-adapter#trackinfopayload)

원본 이벤트가 부분 변경인지 전체 스냅샷인지 확인한 뒤 병합한다. 서로 다른 곡의 필드를 병합하지 않는다. 누락된 위치는 0초로 만들지 않고 ‘위치 불명’으로 둔다.

프로세스 기반 어댑터는 중복 실행 방지, 표준 출력 버퍼 정리, 종료 시 자식 프로세스 정리가 필요하다. 종료가 확인되면 제한된 횟수로만 재시작하고 실패 상태를 사용자에게 보여 준다.

## 10. LRCLIB 연동 방식

### 10.1 요청과 응답

기본 요청은 `GET https://lrclib.net/api/get`이다.

| 입력 | 전달 정책 |
| --- | --- |
| track_name | 원본 제목의 앞뒤 공백 정리, 필수 |
| artist_name | 원본 아티스트의 앞뒤 공백 정리, 필수 |
| album_name | 존재하면 전달 |
| duration | 유한하고 1~3600초인 값만 전달; 길이를 임의로 범위 안에 잘라 넣지 않음 |

URL 문자열을 직접 이어 붙이지 않고 `URLComponents`로 한글·공백·`&`를 인코딩한다. `User-Agent`에는 앱 이름·버전과 실제 프로젝트 URL 또는 연락처를 넣는다. 개인 식별자나 청취 기록은 헤더에 넣지 않는다.

공식 문서는 길이를 제공할 때 약 ±2초 범위의 일치를 설명한다. 검색은 `/api/search`의 `track_name`, `artist_name`을 사용하며 `q`와 구조화 검색 인자를 섞지 않는다. 현재 검색 결과는 최대 20개이고 페이지네이션이 없다. 이 수치는 서비스 변경 가능성이 있으므로 구현 시 다시 확인한다. [LRCLIB 조회·검색 문서](https://lrclib.net/docs#supported-endpoints)

### 10.2 MVP 조회 정책

1. 메모리 캐시가 있으면 사용한다.
2. 확보한 곡 정보로 `/api/get`을 한 번 호출한다.
3. 반환 곡의 제목·아티스트·버전 표기와 알려진 길이를 비교한다. 길이가 같다고 같은 곡은 아니다.
4. 일치하면 `instrumental` → 유효한 `syncedLyrics` → `plainLyrics` → 가사 없음 순으로 상태를 결정한다.
5. 404 또는 애매한 결과는 ‘가사를 찾지 못했어요’나 ‘곡 확인이 필요해요’로 끝낸다. 자동으로 여러 조건을 무한 재검색하지 않는다.
6. P1에서 검색 후보 목록과 수동 선택을 추가한다. 제목·아티스트·길이 차이·앨범·동기화 여부를 표시한다.

문자열 정규화는 Unicode 정규화, 공백 정리, 비교용 영문 대소문자 통일부터 시작한다. `Live`, `Remix`, `Remastered`, `Instrumental` 등 버전 구분은 지우지 않는다. 검색 결과의 첫 번째 항목이나 동기화 가사가 있다는 이유만으로 자동 선택하지 않는다.

### 10.3 통신과 캐시 설계값

- 요청은 전역에서 하나씩 처리하고 요청 사이에 300ms 간격을 둔다.
- 요청 제한 시간은 초기 10초로 설정하고 실측 후 조정한다.
- 429·503의 `Retry-After`를 존중한다. 대기 중에는 다음 곡 요청도 제한을 지키며 최신 요청만 남긴다.
- 일시적 서버·네트워크 오류는 현재 곡에 한해 최대 2회 재시도한다. 헤더가 없으면 1초·3초 지연을 사용한다.
- 400은 입력 문제로 처리하고 자동 재시도하지 않는다. 404는 같은 곡에서 즉시 반복하지 않는다.
- 상태 코드와 Content-Type을 먼저 확인한다. 오류 본문이 HTML이나 일반 텍스트일 수도 있다.
- 성공 캐시는 앱 실행 동안 최대 100곡, 미등록 캐시는 10분으로 시작한다. 수동 새로고침도 요청 제한을 준수한다.
- 디스크 캐시는 P2로 미룬다. HTTP 자체의 영구 캐시도 의도치 않게 생기지 않도록 세션 설정을 검토한다.

시간·용량·재시도 횟수는 이 프로젝트의 초기 설계값이며 LRCLIB가 보장하는 수치가 아니다. 공식 문서는 순차 요청, 짧은 간격, 제한 응답 대응을 요구한다. 현재 문서에 없는 과거 `/api/get-cached` 경로에 MVP를 의존시키지 않는다. [LRCLIB 구현 요구사항](https://lrclib.net/docs#implementation-requirements)

## 11. LRC 파싱과 동기화 로직

### 11.1 지원 문법

MVP는 줄 단위 LRC의 다음 부분집합을 지원한다. 문법 변형은 지원 범위를 README에 명시한다.

```lrc
[ar:테스트 아티스트]
[ti:직접 만든 테스트 곡]
[offset:0]
[00:02.50]첫 번째 테스트 줄
[00:05.000][00:12.00]두 번 등장하는 테스트 줄
[00:08]정수 초 타임스탬프
[00:10.00]
```

위 가사는 검증용으로 작성한 합성 문구다.

- `[mm:ss]`, `[mm:ss.d]`, `[mm:ss.dd]`, `[mm:ss.ddd]`를 처리한다. 소수부는 자릿수에 따라 0.1·0.01·0.001초로 해석한다.
- 한 줄의 여러 타임스탬프를 각각 펼친다.
- 메타데이터 태그는 표시 가사에서 제외하고 `[offset:정수]`는 문서 보정값으로 보존한다.
- 분은 2자리 이상도 허용하고 초는 0 이상 60 미만으로 검증한다.
- 타임스탬프순으로 안정 정렬하고 같은 시각의 서로 다른 문구는 하나의 그룹에 보존한다.
- 같은 시각·같은 문구만 중복 제거한다. 다른 시각의 반복 가사는 삭제하지 않는다.
- 빈 문구에도 유효한 시각이 있으면 가사 지우기 이벤트로 유지한다.
- 잘못된 줄은 건너뛰고 진단 개수를 남긴다. 유효한 줄이 전혀 없으면 일반 가사로 전환한다.
- 원본을 보존하고, UTF-8 BOM과 CRLF를 처리한다. 앱 설계 상 입력은 1MB·10,000개 cue를 상한으로 제한한다.
- Enhanced LRC의 단어별 태그는 MVP에서 지원하지 않는다. 해당 입력은 일반 가사로 전환해 태그를 그대로 노출하지 않는다.

### 11.2 재생 시계

기준 시점의 위치를 `p0`, 단조 시계의 기준을 `t0`, 현재를 `t`, 속도를 `r`이라 하면:

```text
재생 중: position = p0 + (t - t0) × r
정지 중: position = p0
known duration이 있으면 최종 재생 위치를 0...duration으로 제한
```

재생 상태가 unknown이거나 위치가 없으면 임의로 시간이 흐른다고 추정하지 않는다. `isPlaying=false`이면 과거의 속도 1이 남아 있어도 정지 상태를 우선한다. 재생 중임이 확실하지만 속도만 없는 경우의 1배속 가정은 공급자별로 명시하고 검증한다.

이벤트 수신 시 새 위치로 기준을 다시 잡는다. 앞뒤 탐색은 증가만 하는 인덱스로 처리하지 않는다. 잠자기 복귀 직후에는 보간을 잠시 멈추고 새 스냅샷을 받아, 잠든 동안의 시간이 잘못 더해지지 않게 한다.

### 11.3 가사 인덱스 선택

```text
lyricTime = position + fileOffsetMilliseconds / 1000
                     + userAdvanceMilliseconds / 1000

현재 그룹 = startSeconds <= lyricTime을 만족하는 마지막 그룹
```

앱의 보정 부호는 **양수이면 가사를 더 일찍 표시**하도록 정의한다. 예를 들어 +500ms이면 10초 가사가 재생 위치 9.5초에 나타난다. 파일 offset도 이 관례로 해석하며 양수·음수 고정 예제로 검증한다. 다른 도구에서 만든 LRC와 해석이 다르면 사용자 보정으로 조정할 수 있게 한다. 보정은 한 번만 적용하며 cue 시각과 조회 시각 양쪽에 중복 적용하지 않는다.

첫 타임스탬프 전에는 현재 줄이 없다. 빈 cue에서는 문구를 지운다. 마지막 cue는 곡 끝까지 유지하되, 실제 종료·새 곡 이벤트가 오면 지운다. 위치가 끝에 도달해도 반복 재생 여부를 임의로 추정하지 않는다.

현재 그룹 검색은 이진 탐색으로 구현한다. 가사 수가 적어 단순 순회도 가능하지만, 이진 탐색의 경계 조건을 테스트하고 한 가지 방식만 유지한다.

### 11.4 화면 갱신과 정확도

가사 화면이 보이고 재생 중일 때만 약 100ms 간격으로 현재 그룹을 계산한다. 실제 SwiftUI 상태는 그룹 인덱스가 바뀔 때만 갱신한다. 정지·숨김 상태에서는 판정 타이머를 멈추고, 오버레이를 다시 표시할 때 현재 시계로 즉시 계산한다. 슬라이딩의 프레임 보간은 SwiftUI 애니메이션에 맡긴다. 100ms 판정 타이머로 이동 좌표를 한 칸씩 갱신하지 않는다.

10분 합성 재생 테스트에서 타이머 누적 오차가 없어야 한다. 로직의 경계 판단과 화면 갱신 지연은 분리 측정한다. 실제 음악의 가사 오차에는 LRCLIB 원본 타이밍, 앱 보고 지연, Bluetooth 출력 지연도 포함되므로 ‘항상 0.1초 정확도’를 약속하지 않는다.

## 12. 투명 가사 오버레이 UI와 슬라이딩 설계

### 12.1 필수 시각 규칙

| 요소 | 확정 동작 |
| --- | --- |
| 표시 방식 | 앱 실행 후 가사를 자동으로 띄우는 오버레이 |

| 주변 줄 | 이전 줄은 위, 다음 줄은 아래; 초기 목표는 현재 줄 포함 5개 cue |
| 전환 | 기존 가사 묶음이 위로 이동하고 아래에서 새 가사 한 줄이 진입 |
| 조작 | 가사 위에 버튼을 두지 않고 배경 앱의 클릭을 통과 |

회색은 흰 글자의 opacity를 낮춰 만들지 않는다. 글자 불투명도는 유지하며 RGB 색상만 바꾼다. 경계에서도 페이드 마스크를 쓰지 않고 영역 밖만 잘라낸다. 밝은 화면 위의 낮은 대비는 실제 화면에서 검증하되 기본 색상과 투명 배경을 자동으로 바꾸지 않는다.

폰트는 한글·영문을 지원하는 24pt 이탤릭을 초기값으로 사용한다. 한글 대체 폰트에서 이탤릭이 적용되지 않으면 기울어진 렌더링이 가능한 폰트 또는 텍스트 변환을 검토하고 라이선스를 확인한다. 기울어진 글자 끝이 잘리지 않도록 좌우 여백을 확보한다. 최종 크기는 가독성 검증 후 조정하되 회색·흰색·이탤릭 규칙은 유지한다.

### 12.2 화면 위치와 좌표

화면 전체를 기준으로 가로 폭을 반으로, 세로 높이를 3등분한다. 아래 구분선은 설명용이며 실제 화면에는 표시하지 않는다.

```text
┌───────────────────┬────────────────────────┐
│                   │     이전 가사 — 회색    │
│                   │     현재 가사 — 흰색    │ ← 이 칸의 중앙
│                   │     다음 가사 — 회색    │
├───────────────────┼────────────────────────┤
│                   │                        │
├───────────────────┼────────────────────────┤
│                   │                        │
└───────────────────┴────────────────────────┘
```

화면의 왼쪽 위를 `(0, 0)`, 폭을 `W`, 높이를 `H`라 하면 영역은 `x=W/2, y=0, width=W/2, height=H/3`이고 중앙은 `(3W/4, H/6)`이다. `visibleFrame`으로 화면 자체를 다시 나누지 않고 **전체 화면 frame으로 6등분**한다. 메뉴바나 노치와의 겹침은 내부 가사 여백으로 처리한다.

AppKit의 화면 좌표 원점을 반영한 패널 프레임 계산 초안은 다음과 같다. 모든 값은 픽셀이 아닌 포인트 단위다.

```text
screen = 대상 NSScreen.frame
panel.x = screen.minX + screen.width / 2
panel.y = screen.minY + screen.height * 2 / 3
panel.width  = screen.width / 2
panel.height = screen.height / 3
```

초기 구현은 앱 시작 때 선택한 주 디스플레이 하나를 사용하고, 다른 앱에 포커스를 옮겨도 대상 화면을 바꾸지 않는다. 디스플레이 연결·해제, 해상도·배율 변경 시 다시 배치한다. 대상 화면이 없어지면 사용 가능한 주 디스플레이로 돌아간다. 수동 드래그로 지정 영역 밖으로 옮기는 기능은 제공하지 않는다. [Apple NSScreen.frame](https://developer.apple.com/documentation/appkit/nsscreen/frame)

### 12.3 투명 창 구성

테두리 없는 비활성화 패널을 사용하고 `isOpaque=false`, 배경색 clear, `hasShadow=false`를 적용하는 방향으로 구성한다. SwiftUI 루트와 호스팅 뷰에도 배경·Material을 넣지 않는다. **창 전체 alpha를 0으로 만들면 글자도 사라지므로 창 alpha는 1로 유지한다.**

일반 앱 창 위에서 표시하고 키보드 포커스를 빼앗지 않는다. `ignoresMouseEvents`를 사용해 가사 뒤의 앱을 클릭할 수 있게 한다. 앱 전환 시 가사 패널이 사라지지 않는지도 검증한다. 전체 화면 앱과 모든 Space 위의 표시는 별도 호환성 검증 후 확장한다. [Apple NSPanel](https://developer.apple.com/documentation/appkit/nspanel), [클릭 통과 속성](https://developer.apple.com/documentation/appkit/nswindow/ignoresmouseevents)

설정·표시/숨김·새로고침·종료는 별도 제어 창에서 제공한다. Dock 등으로 앱을 활성화하면 제어 창을 열 수 있게 하고, 가사 표시는 그 창을 열지 않아도 계속된다. 메뉴바 항목을 추가하더라도 관리용 보조 수단으로만 사용한다.

### 12.4 현재 가사 중앙 유지

가사 콘텐츠를 수직으로 배치하고 각 cue의 실제 렌더링 높이를 측정한다. 현재 cue의 콘텐츠 내부 중심 좌표를 `cueCenter`, 가사 영역 높이를 `viewportHeight`라 하면 목표 이동량은 다음과 같다.

```text
targetOffsetY = viewportHeight / 2 - cueCenter
```

이동값을 리스트 전체에 적용하고 가사 영역 밖은 clip한다. 첫 줄과 마지막 줄에서도 중앙 배치가 가능하도록 위아래 여유 공간을 충분히 확보한다. 곡 처음에는 위쪽 빈 공간, 마지막에는 아래쪽 빈 공간을 허용한다.

긴 가사는 같은 cue 안에서 줄바꿈하고 **그 텍스트 블록의 중심**을 중앙 기준으로 삼는다. 같은 타임스탬프에 여러 가사가 있으면 하나의 cue 블록으로 함께 흰색 강조한다. 주변 cue는 공간에 맞춰 줄이되 현재 cue는 생략하지 않는다. 현재 블록도 영역보다 길면 최소 글자 크기까지 축소하고, 그래도 넘치면 중앙 요약 표시와 제어 창의 전체 본문으로 처리한다.

### 12.5 다음 줄 전환 애니메이션

1. 재생 시간이 다음 cue의 시작을 넘으면 현재 인덱스를 갱신한다.
2. 기존 현재 줄은 회색, 새 현재 줄은 흰색으로 즉시 변경한다. 단어 단위로 색을 채우지 않는다.
3. 새 현재 cue가 중앙에 오도록 전체 묶음의 Y offset을 위로 애니메이션한다.
4. 위쪽 줄은 영역 밖으로 나가고, 아래에서 새로운 후속 cue 한 줄이 올라온다. 이동 전에 아래쪽 추가 cue를 준비해 빈 공간이나 깜빡임을 막는다.
5. 이동 완료 후에도 새 현재 cue의 중심과 영역 중심이 일치해야 한다.

초기 전환 시간은 240ms, ease-in-out으로 정한다. 줄바꿈이 있으면 고정 행 높이가 아니라 측정한 cue 중심 사이의 거리만큼 이동한다. ‘항상 가운데’는 **현재 cue의 정착 위치와 자동 스크롤 기준을 중앙으로 고정**한다는 의미다. 요청한 슬라이딩을 위해 전환 중 새 현재 줄이 아래에서 중앙으로 이동하는 짧은 구간은 존재하며, 완료 후 중앙에서 벗어난 상태를 허용하지 않는다.

처음에는 전체 cue를 배치한 단순 VStack과 clip으로 구현한다. 프로파일링에서 필요할 때만 현재 주변 cue와 위아래 진입용 여분 cue를 유지하는 방식으로 최적화한다. 가사 색상 변경으로 크기나 굵기가 바뀌어 레이아웃이 흔들리지 않게 한다.

### 12.6 탐색·정지·빠른 전환·접근성

- 정상적인 한 cue 진행만 위쪽 슬라이딩을 사용한다.
- 여러 cue를 건너뛰는 탐색·역방향 탐색·곡 교체·복귀는 기존 애니메이션을 취소하고 대상 cue를 즉시 중앙에 배치한다.
- 애니메이션 도중 다음 cue가 도착하면 현재 시각의 목표로 재설정한다. 지난 전환을 큐에 쌓아 재생보다 늦어지지 않게 한다.
- 일시 정지하면 새 cue 진행을 멈춘다. 이미 시작한 짧은 전환은 중앙까지 마친 뒤 유지한다.
- Reduce Motion 설정에서는 슬라이딩을 생략하고 중앙 배치와 색 변경만 수행한다.
- VoiceOver 레이블을 제공하되 줄 전환마다 강제 음성 알림을 반복하지 않는다.

### 12.7 가사 없는 상태와 설정

로딩·미등록·연주곡·오류는 같은 영역 중앙에 짧은 회색 상태 문구로 표시한다. 재생 세션이 없으면 가사 오버레이를 비워 화면을 가리지 않고, 자세한 상태는 제어 창에서 확인한다.

일반 가사만 있거나 재생 위치를 모르면 현재 줄을 임의로 추정하지 않는다. 오버레이에 ‘동기화 정보 없음’ 또는 ‘재생 위치 확인 불가’를 표시하고 제어 창에서 일반 가사 전체를 읽게 한다. 일시 정지는 기존 현재 가사를 유지한다.

P1 시간 보정은 제어 창에 ‘가사를 0.1초 앞당김 / 늦춤’으로 제공한다. 초기 범위는 ±5초이며 초기화 버튼을 둔다. 글자 크기를 바꾸면 높이를 다시 측정해 현재 cue를 중앙에 재배치한다.

App Store 심사 지침 2.5.1은 공개 API 사용을 요구한다. 외부 어댑터를 사용해도 비공개 API 의존성이 사라지는 것은 아니다. [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#software-requirements)

**API 접근 허용, 서버 코드 라이선스, 개별 가사의 저작권은 서로 다른 문제다.** 무료 조회 가능하다는 사실만으로 가사 전문의 재배포·공개 저장·상업 이용 권한을 얻었다고 판단하지 않는다. 이 계획서는 해당 권리가 확보되었다고 전제하지 않는다.

발표 자료와 공개 저장소에는 직접 쓴 합성 가사 또는 이용 권한이 확인된 자료를 사용한다. 실제 곡 가사 전문을 테스트 fixture·스크린샷·README에 넣지 않는다. 캐시는 기본 메모리에만 보관하고, 배포나 영구 저장을 확장할 때 LRCLIB의 최신 정책과 필요한 권리를 확인한다. 출처 표시는 권리 허락의 대체가 아니다.

| 실제 재생 세션 없음 | 가사·시계 해제, 오버레이 비움 | 제어 창에 재생 중인 곡이 없어요 |
| 공급자 시작 실패 / 시간 초과 | 한정 재연결, 모의 모드는 별도 선택 | 현재 곡 정보를 읽을 수 없어요 |
| 제목·아티스트 누락 | 조회 대기, 빈 값으로 요청 금지 | 곡 정보를 확인하고 있어요 |
| 위치 누락 | 가사는 읽되 자동 강조 중단 | 재생 위치를 확인할 수 없어요 |
| 404 | 미등록 캐시 | 가사를 찾지 못했어요 |
| 일반 가사만 존재 | 오버레이에 상태, 제어 창에 일반 가사 | 동기화 정보가 없는 가사예요 |
| instrumental=true | 빈 가사를 오류로 처리하지 않음 | 연주곡이에요 |
| 오매칭 의심 | 결과 적용 보류 | 곡 확인이 필요해요 |
| 429 / 503 | Retry-After 대기, 반복 버튼도 제한 | 잠시 후 다시 시도해 주세요 |
| 오프라인 / 5xx | 캐시 유지, 제한적 재시도 | 가사를 불러오지 못했어요 |
| 잘못된 JSON / LRC | 안전하게 실패 또는 일반 가사 전환 | 가사 형식을 읽을 수 없어요 |
| 빠른 곡 변경 | 취소 + 세대 검증 | 새 곡의 로딩 상태 |
| 탐색·정지·재개 | 시계 기준 재설정, 인덱스 재탐색 | 즉시 새 위치 반영 |
| 잠자기 복귀 | 새 스냅샷 요청 후 보간 재개 | 필요하면 잠시 연결 중 |
| 어댑터 프로세스 종료 | 제한적 재시작, 종료 시 자원 회수 | 연결이 끊겼어요 |

빈 응답 하나만으로 ‘재생 없음’과 ‘권한·호환성 실패’를 완벽히 구별할 수 없을 수 있다. 가능한 진단 정보를 함께 보며, 불확실하면 ‘정보를 읽을 수 없음’으로 표시한다.

| Synchronizer | 첫 줄 이전, 경계 직전·정확히 경계·직후, 마지막 줄 | 정의한 그룹 선택 |
| PlaybackClock | 정지·재개, 속도, 앞뒤 탐색, 장시간 진행 | 가상 시계로 기대 위치 검증 |
| 시간 보정 | +500ms와 -500ms, 파일+사용자 보정 | 방향과 단일 적용 검증 |
| LRCLIBClient | 한글·특수 문자, null 가사, 추가 JSON 필드 | 요청 인코딩·디코딩 성공 |
| HTTP 처리 | 400·404·429·503, 비JSON 오류, 시간 초과 | 오류 분류·재시도 정책 준수 |
| 비동기 상태 | A→B→A 전환, 과거 응답 역순 도착 | 마지막 조회 세대만 적용 |
| 캐시 | 재생 위치 변경, 동일 곡 재방문, 만료 | 불필요한 재요청 없음 |

통신 테스트는 `URLProtocol` 기반 응답 대역으로 작성한다. 테스트 실행 때 실제 LRCLIB를 반복 호출하지 않는다. 시계 테스트는 실제 10분을 기다리지 않고 시간을 주입한다.

### 실제 Mac 통합 테스트

주 지원 음악 앱 하나에서 다음을 수행하고 OS·앱·빌드 정보를 기록한다.

1. 동기화 가사 확보 곡 3개 이상, 일반 가사·미등록·연주곡은 확보 가능한 실제 사례 또는 명시적인 Mock으로 검사한다.
2. 곡 변경 10회, 정지·재개 5회, 앞뒤 탐색 각 5회, 같은 곡 반복을 검사한다.
3. 음악 앱 종료·재실행, 인터넷 차단·복구, 잠자기·복귀를 검사한다.
4. 오버레이 표시·숨김 20회에서 패널·리스너·타이머가 늘어나지 않는지 확인한다.
5. 30분 연속 실행에서 크래시·지속적인 메모리 증가·남아 있는 자식 프로세스가 없는지 확인한다.

### 오버레이 UI 검증

- 앱 실행 후 메뉴바 클릭 없이 가사가 자동으로 나타나는지 확인한다.
- 화면을 2열·3행으로 계산했을 때 패널이 오른쪽 위 칸에 있는지 검사한다. 다른 해상도·Retina 배율에서도 포인트 좌표를 확인한다.
- 체크무늬 테스트 배경 위에서 사각 배경·블러·그림자 없이 글자만 보이는지 검사한다.
- 회색 `#8E8E93`와 흰색 `#FFFFFF`의 alpha가 각각 1인지 확인하고 한글·영문의 이탤릭을 눈으로 검증한다.
- 첫 cue·중간 cue·마지막 cue·긴 가사·동일 시각 여러 줄에서 전환 완료 후 현재 cue 중심 오차가 1pt 이내인지 확인한다.
- 연속 20회 전환에서 기존 줄이 위로 이동하고 아래 새 줄이 올라오는지, 역방향 순간 점프·깜빡임·누적 지연이 없는지 확인한다.
- 240ms보다 짧은 간격의 합성 cue와 애니메이션 중 탐색을 검사한다. 최종 위치가 최신 재생 상태를 따라야 한다.
- 가사 뒤의 앱 클릭과 키보드 입력이 정상이며, 앱 전환으로 오버레이가 숨겨지지 않는지 확인한다.
- 화면 연결·해제와 크기 변경 시 영역을 재계산하고 Reduce Motion에서 즉시 배치되는지 확인한다.

### 측정 목표

- 모의 공급자 이벤트 수신 후 화면 상태 반영: 300ms 이내를 목표로 측정한다.
- 실기기 곡 변경·탐색 인식: 이벤트 방식은 2초 이내 목표, 폴링 대안은 폴링 주기를 포함해 별도 기록한다.
- 가사 경계 판정과 흰색 강조 시작: 합성 데이터에서 200ms 이내 목표. 슬라이딩 정착 시간 240ms와 외부 가사 자체의 오차는 별도 측정한다.
- 숨김·정지 상태에서 불필요한 고빈도 타이머가 없어야 한다.
- 실제 CPU·메모리 사용량을 같은 Mac에서 측정해 README에 기록한다. 하드웨어와 무관한 수치를 보장하지 않는다.
- 네트워크 조회 시간과 가사 보유율은 외부 서비스 조건이므로 앱 내부 성능 지표와 나누어 기록한다.

### 한 번의 작업 루프

1. **한 가지 사용자 동작**과 완료 기준을 정한다.
2. Codex에 현재 구조를 읽고 변경 범위를 설명하게 한다.
3. 작은 기능을 구현하고 관련 테스트·빌드를 실행한다.
4. 학생이 실제 앱에서 재현 절차를 수행한다.
5. 실패하면 기대 결과·실제 결과·재현 순서·개인정보를 제거한 로그를 전달한다.
6. 통과한 상태를 커밋하고 다음 기능으로 넘어간다.

한 프롬프트에 전체 앱·오버레이 애니메이션·API·배포를 함께 맡기지 않는다. 새 기능이 실패하면 기존 통과 상태로 돌아갈 수 있어야 한다. Codex가 ‘완료’라고 말해도 실행하지 않은 항목은 검증 완료로 표시하지 않는다.

### 단계별 Codex 요청 예시

**A. 뼈대와 모의 재생기**

> 현재 폴더를 확인하고 AppKit NSPanel과 SwiftUI로 투명 가사 오버레이의 최소 구조를 만들어 줘. 전체 화면을 2열·3행으로 나눈 오른쪽 위 칸에 배치하고, 배경 없이 불투명한 회색 이탤릭 가사와 흰색 현재 줄을 보여 줘. MockNowPlayingProvider를 사용하며 메뉴바 클릭 없이 자동 표시해 줘. 뒤의 앱 클릭을 통과시키고 현재 cue 블록의 중심을 영역 중앙에 맞춰 줘. 내가 Xcode에서 확인할 순서를 알려 줘.

**B. MediaRemote 가능성 검증**

> 현재 macOS·Xcode·패키지 버전을 확인하고 NowPlayingProvider 뒤에 MediaRemote 어댑터를 연결하는 작은 실험을 만들어 줘. 비공개 API가 동작한다고 가정하지 말고 제목·위치·정지·탐색 이벤트 수신 여부를 검증할 수 있게 해 줘. 시스템 보안 설정 변경 없이 진행하고 실제 실행하지 못한 검증은 별도로 표시해 줘.

**C. 파서와 동기화**

> LRCParser와 LyricsSynchronizer만 구현해 줘. 여러 타임스탬프, 동일 시각 여러 줄, 빈 cue, 양수·음수 offset과 앞뒤 탐색을 지원해 줘. +500ms는 가사를 0.5초 앞당기는 규칙이야. 합성 입력과 가상 시계로 경계 테스트를 작성하고 결과를 알려 줘.

**D. LRCLIB 조회**

> LRCLIB 공식 문서를 확인한 뒤 URLSession 기반 클라이언트를 구현해 줘. 식별 User-Agent, 순차 요청, Retry-After, null 가사와 비JSON 오류를 처리해 줘. 곡 변경으로 취소된 과거 응답이 화면에 적용되지 않는 회귀 테스트를 넣어 줘. 실제 API를 반복 호출하는 테스트는 만들지 마.

**E. 중앙 유지와 슬라이딩**

> 현재 cue의 실제 높이를 측정해 가사 영역 중앙에 정렬해 줘. 다음 cue로 넘어가면 기존 줄은 회색, 새 현재 줄은 흰색으로 바꾸고 전체 가사를 240ms 동안 위로 슬라이딩해 줘. 아래에서 후속 cue가 진입하도록 하고 글자 alpha는 1로 유지해 줘. 긴 줄, 첫 줄·마지막 줄, 연속 전환과 탐색 취소를 검증하고 Reduce Motion도 처리해 줘.

**F. 통합 검토**

> MVP 완료 기준에 따라 현재 구현을 검토해 줘. 특히 중복 리스너, 일시 정지 시 시간 증가, 이중 보간, 곡 전환 경쟁 상태, 앱 종료 후 자식 프로세스 잔존을 확인해 줘. 발견한 문제를 재현 가능한 항목으로 정리하고 높은 영향의 문제부터 수정·검증해 줘.

## 17. 개발 순서와 단계별 완료 기준

개발 기간이나 주차는 배정하지 않는다. 각 단계의 동작을 검증한 뒤 다음 단계로 진행하며, 고등학생 개인 프로젝트에 맞게 하나의 음악 앱과 하나의 화면에서 핵심 흐름을 완성한다.

| 단계 | 구현 내용 | 완료 기준 |
| --- | --- | --- |
| 1. 연동 가능성 확인 | 환경 기록, MediaRemote 최소 실험, 공급자 경로 결정 | 제목·위치·정지·탐색 수신 증거 또는 대체 경로 확보 |
| 2. 오버레이 뼈대 | 투명 NSPanel, 오른쪽 위 1/6 배치, Mock 데이터 | 메뉴바 클릭 없이 글자만 자동 표시, 뒤의 앱 조작 가능 |
| 3. 정적 가사 레이아웃 | 회색 이탤릭, 흰색 현재 cue, 중앙 기준, 긴 가사 | 첫·중간·마지막 cue와 여러 줄에서도 중앙 정렬 |
| 4. 조회와 파싱 | LRCLIB, 캐시, 오류 처리, LRCParser | 정상·미등록·잘못된 입력 테스트 통과 |
| 5. 동기화와 이동 | PlaybackClock, 현재 cue 판정, 위쪽 슬라이딩 | 정지·재개·탐색 처리와 아래 새 줄 진입 검증 |
| 6. 실제 재생 통합 | 실제 공급자 연결, 취소·세대 검증 | 실제 곡 전환에서 과거 가사 노출·이중 보간 없음 |
| 7. 안정화 | 복귀·화면 변경·접근성·자원 정리 | 기능·UI 회귀 검사와 연속 실행 통과 |
| 8. 문서화 | 실행 방법, 검증 환경, 제한, 데모·회고 | 실제 연동과 Mock을 구분한 재현 가능한 결과물 |

범위를 줄여야 하면 수동 검색, 설정 확장, 디스크 캐시를 뒤로 미룬다. **투명 배경, 오른쪽 위 1/6 배치, 회색 이탤릭·흰색 현재 줄, 중앙 유지와 슬라이딩은 핵심 요구사항이므로 선택 기능으로 내리지 않는다.**

- [ ] 2~3분 발표: 곡 변경 → 동기화 → 정지·탐색 → 오류 처리
- [ ] 구조도, 시간 계산 설명, Codex 도움과 직접 검증 범위를 적은 회고
- [ ] 가사 전문·청취 기록·비밀 값이 저장소에 없는지 확인

학생이 설명할 수 있어야 할 질문: ‘왜 0.1초씩 시간을 더하지 않는가?’, ‘이전 곡 응답이 늦게 오면 어떻게 막는가?’, ‘일시 정지는 어디서 처리하는가?’, ‘동일 시각의 두 줄은 어떻게 표시하는가?’, ‘MediaRemote가 막혀도 어떤 부분을 그대로 쓸 수 있는가?’

## 20. 확인한 출처와 조사 한계

아래 문서는 2026-10-14에 확인했다. API·정책은 구현 시작 때 다시 확인한다.

1. [LRCLIB 공식 API 문서](https://lrclib.net/docs): 현재 조회 인자, 응답 필드, 클라이언트 식별, 요청 제한.
2. [ungive/mediaremote-adapter](https://github.com/ungive/mediaremote-adapter): 비공개 MediaRemote 접근 방식과 15.4 이후 제약에 대한 구현자 설명.
3. [ejbills/mediaremote-adapter](https://github.com/ejbills/mediaremote-adapter): Swift 래퍼, 수신 이벤트와 재생 시간 필드.
4. [Apple NSPanel](https://developer.apple.com/documentation/appkit/nspanel), [NSScreen.frame](https://developer.apple.com/documentation/appkit/nsscreen/frame), [ignoresMouseEvents](https://developer.apple.com/documentation/appkit/nswindow/ignoresmouseevents): 오버레이 패널·화면 좌표·클릭 통과.
5. [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#software-requirements): 공개 API 사용 요구.
6. [Apple NSAppleEventsUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription): Apple Events 사용 목적 설명.

이 문서는 개발 계획서이며 앱 구현·실기기 연동 테스트 결과가 아니다. MediaRemote의 현재 기기 호환성, 개별 곡의 LRCLIB 등록 여부, 가사 이용 권리는 이번 문서 작성만으로 확인된 것으로 간주하지 않는다.
